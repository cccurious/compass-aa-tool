# 診断ファースト（実装の前に測る）

ヒューリスティック（検出・推定・清掃・様式化…）は「実装してみて目で確かめる」と
必ず失敗する: 主観評価は揺れ、退行に気づけず、効かない機能に工数が沈む。
**実装より先に、正解が分かる計測を作る。** 本プロジェクトでの実績:
位相追従 J（診断で前提不成立と判明→最小実装で済んだ）・色数提案（診断で
AA 過大が主因と特定→凍結判断が数字で下せた）・内部暗線（診断で手掛かり不在と
判明→実装せず解像度案内で解決）。3 件とも**診断が実装より安かった**。

## 手順

1. **問いを 1 文にする**: 「◯◯という手掛かりは、入力データに機械検出可能な形で
   実在するか？」——機能の可否はほぼ常にこの形に還元できる。
2. **正解既知の合成データを作る**（最重要）:
   - 制御変数を厳密に固定した入力を決定論スクリプトで生成する
     （例: 色数 K を厳密に K 色で作る／既知量のドリフトを注入する）。
   - スクリプトは scripts/ へ、出力はコミット対象外の置き場へ。
   - **測定器の校正**: まず合成に対して測定が正解を復元できるかを確認する。
     測れない測定器で実データを測らない。
3. **実データで手掛かりの存在を測る**: 合成で校正済みの測定を実データに当て、
   手掛かりの強さ・分布を数値と可視化（オーバーレイ画像等）で出す。
4. **判定**:
   - 手掛かりが明確 → 実装へ。診断ハーネスはそのまま合格ゲートに転用する。
   - 手掛かりが弱い/ノイズと不可分 → **実装しないことを成果として報告**する
     （「無い線は引けない。引けば幻覚」）。代替案（ユーザー操作・解像度・既存機能）を添える。
   - どちらとも言えない → 判定に足りない素材・情報を特定してユーザーに要求する。
5. **結果を固定する**: 診断の数字・判定・再訪条件を設計資料へ記録する。
   これが無いと後続セッションが同じ診断を繰り返す。

## 掟

- 診断コードは使い捨てで良い（scratchpad 可）が、**数字と結論は必ず永続化**する。
- 診断の前に既存の設計資料・過去の棄却理由を読む（同じ検討の繰り返しが最大の無駄）。
- 「1 点だけ良くして他を壊す」を防ぐため、診断には必ず**対照群**（正常系・
  既存が上手くいっているケース）を含める。
- 診断が「効く」と言っても、実装の合格ゲートは別途書く（write-plans Skill 参照）。
